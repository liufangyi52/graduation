# 系统架构

## 1. 目标与边界

MeetingFlow AI 面向项目团队，将会议纪要转化为可复核的摘要、决策、候选任务、分派建议和风险提示，并提供任务进度跟踪能力。

当前实现是可独立运行的演示型 MVP：分析服务以 `mock` 模式返回受控草稿，不调用外部大模型，也不应被描述为真实模型推理或已上线 RAG 系统。

系统的关键业务约束是人工复核：会议分析结果必须由项目经理确认后，才能形成正式任务。

## 2. 服务组成

| 服务 | 路径 | 技术 | 默认端口 | 职责 |
| --- | --- | --- | --- | --- |
| 前端 | `apps/web` | Vue 3、Vite、TypeScript | 5173 | 展示会议、候选任务、项目和进度数据；调用 REST API。 |
| API | `apps/api` | NestJS、TypeScript | 3000 | 提供 `/api` REST 接口、输入校验、演示账号与内存种子数据。 |
| AI 服务 | `apps/ai` | FastAPI、Pydantic | 8000 | 提供受控分析草稿和健康检查；当前为 mock 模式。 |

本地开发时，Vite 将前端的 `/api` 请求代理至 `http://localhost:3000`。API 服务使用全局前缀 `/api`。

## 3. 核心流程

1. 项目经理提交会议标题、纪要文本、日期和参会人。
2. API 创建会议记录并发起分析。
3. 分析服务产生带来源片段的摘要和候选结果；结果状态为待复核。
4. 项目经理选择候选任务并确认，系统再创建或更新正式任务。
5. 团队成员更新任务状态、进度和阻塞信息；项目经理查看项目和分析指标。

任何涉及任务抽取的改动都应保留来源证据和人工复核关卡，不能直接将模型草稿作为最终事实。

## 4. 数据与基础设施现状

API 当前使用内存种子数据，重启服务后演示数据会重置。`docker-compose.yml` 定义了 MySQL、Redis、Qdrant 和 MinIO，供后续持久化、缓存、检索和文件存储演进使用；这些服务目前不是演示主流程的必需依赖。

后续接入真实模型或 RAG 前，应补充数据脱敏、访问控制、检索来源追溯、失败降级、评测集和调用观测设计。
